Tender Intelligence — Production Architecture & Process

Drafted 2026-04-27. Reflects the production-target topology, not the local PoC. Companion to docs/project_spec.md § 4 (architecture) and § 5 (resources).

Architectural change from PoC: production uses Azure SQL Database (Serverless) instead of SQLite-in-Blob. Reason: analytics readiness — Power BI, ad-hoc T-SQL, and the future intelligence features (F4–F7) all need a queryable multi-reader store, and migrating later is more painful than starting right. Application code is unchanged except for the connection string. Cost delta: ~€15–40/month on top of the ~€10 infra base.

1. System architecture

Azure-resident components live in CGI's tenant. External services (Hilma, tarjouspalvelu.fi, OpenAI) are reached over the public internet. Both Container Apps Jobs share the same Key Vault, Storage account, and Azure SQL Database. Managed Identity binds the Jobs to Azure resources so no secret ever touches the image.

Second Container Apps Job. Polls the service mailbox via Microsoft Graph Mail, extracts [TENDER-<tp_id>] from reply subjects, updates claim state in the DB. Smaller than the scraper; same Key Vault + DB connection pattern.

What this gives us

Use case How it works on Azure SQL Would it work on SQLite-in-Blob?
Power BI dashboard for stakeholders Native connector, scheduled refresh, row-level security if needed No — would need to dump to a queryable store first
Ad-hoc question: "what's the average award price for IT consulting in Helsinki the last 12 months?" One T-SQL query, run from Azure Portal Query Editor, takes 10 seconds No — would need to download the .db file, query locally, never against fresh data
Competitor profile: "every tender Atea won in 2025" Single query against award_analysis Possible but slow (download → query → discard)
Pricing model training (F6) Scheduled export to Parquet on Blob via T-SQL, train in notebook Possible but every run blocks the live DB
Concurrent reply tracker writes (every 2 h) without losing scraper writes Native row-level locking, no risk Edge case: if scraper overruns, the second writer's changes can be lost
"Who claimed which tender?" in real time Reply tracker writes immediately; dashboard reads next refresh Works but requires the Blob round-trip
What about the document content? ZIP attachments stay in Blob (with Defender scan) and SharePoint (final home), as the diagram shows. Full-text search over their contents is a Future-scope item (F2 — Level 3 AI agents reading attachments). Until then, structured tender metadata in Azure SQL + raw documents in SharePoint is sufficient — every analytical question we expect for MVP is answered by metadata, not by the document body text.
